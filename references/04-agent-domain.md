| 文件 | 作用 |
|---|---|
| `INTERVIEW.md` | 111 道概念题（8 组）+ 6 道系统设计题 + 10 道手撕代码题 + 追问链；每行都是「题号 / 题目 / 一句话要点」 |
| `CHECKLIST.md` | 掌握判定与查漏清单 |

| `code/*.py` | **教学用的可运行示例**，标准库、零配置；不是候选人履历，见 §7 |

## 3. 岗位类别 → 考点包

先按 JD 高频关键词命中题号，再按类型裁剪；**同一考点在全文最多出现 1 次**（见 `02` §4）。

| 岗位类别 | 优先题号 | 典型考点 |
|---|---|---|
| Agent 工程 | 1–22、23–42、99–111 | Agent vs Workflow 选型、最小 loop 五件套、Harness、Function Calling 参数校验、MCP 与 Skills 边界、工具失败降级、幂等与 HITL、提示词注入 |
| 算法 / 模型 | 1–15、43–61、62–74、87–98 | 幻觉与 grounding、上下文预算与压缩、切块与混合检索、重排、RAG 评测、模型评审偏置、幻觉率定义 |
| 平台后端 | 16–22、75–86、99–111 | 状态机与 checkpoint、多 Agent 通信与完成事件、异步消息幂等、超时 / 死锁、权限分级、沙箱、可观测与故障定位 |

- **业务面**：从考点包取 8~10 道，至少 2 道结合公司具体业务 / 产品场景命题；方案设计题最多 2 道（≤450 字）。
- **HR 面**：不出纯技术细节题，只取「业务理解 / 行业判断 / 资源取舍 / 优先级」类，3~5 道；其余容量给行为面与稳定性话题。模拟面试首题从题库 `behavior` 池抽（`L1-BH01`~`03`），**不得强制从技术八股池起手**；升档可用 `L2-BH01`~`02`。
- **系统设计题**：只在用户明确说会考架构 / 白板时启用，套 `INTERVIEW.md` 的答题框架，评分点在边界判断、状态与失败处理、评估方式、成本与安全。
- **手撕代码题**：本 Skill 不做代码陪练；若用户提到，可在章 3 用 1 道题给「思路 + 对应 `code/` 文件」，不展开完整实现。概念题 / 方案题的模拟面试由 `08`、`09` 负责，题库难度池在 `scripts/question_bank.json`。

## 4. 按需读取规则（避免把 30KB 又堆回来）

1. 只读 `INTERVIEW.md` 中命中的题目行，以及对应章节 README 的「易错点」与「三句话」两节。
2. 举例可以指向 `code/` 里**真实存在**的文件与函数（如 `code/01_minimal_react_agent.py` 的 loop、`code/02_function_calling.py` 的 Schema 校验与重试、`code/09_guardrails.py` 的幂等键与 `waiting_approval`），但表述必须是「这个演示实现里」，见 §7。基础八股题没有对应 `code/` 实现时，证据锚用**教材里的公式 / 机制**：缩放点积除以根号 d、teacher forcing、PPO 的 clip 目标、KL 约束项等，不硬凑项目文件。
3. 文档里写「题号 + 一句话要点 + 演示实现例子」，**不复制整章 README**。
4. 知识库是你的**复习资料**，不是公司事实来源，也不是候选人经历来源；公司业务、财报、产品动态一律走 `06` 的事实边界与编号引用。

## 5. 题域标签与 JD 映射

每题（含题库题与文档题）带 `domain_tags`，取值 `basics / llm / agent / multimodal / rag / eval / engineer / research / behavior`。题目内容来自本文件的考点包，**题域配比来自 `10-jd-profile.md`**：

- JD 关键词决定命中哪些题域、各出几道、对应哪些 Q 编号，结果写进章 3 章首的 `### JD 题型映射`；
- 基础八股固定归 `basics`，**业务面 ≥3 题、HR 面 0 题下限**（HR 面改由 `behavior` 题域 ≥2 题约束，见 `rules.json`）；
- 升档换考点（含 `probe` 试探性升档）时用 `pick_questions.py --tags <题域>` 从命中题域抽题，让模拟面试也跟着 JD 走；`behavior` 在 L1 / L2 都有题，不会再出现空池；
- 题目内容与题域不符（表写 `multimodal`、题目全在问 Workflow 选型）属于语义不合格，脚本验不了，由 `07` 勾选。

## 6. 万能回答模板（章 3 / 4 / 5 通用）

`一句话结论 → 为什么（原理 / 动机）→ 可核对的做法与证据 → 代价与替代方案`

「做法与证据」这一段的措辞**取决于证据归属**（§7）：本人已确认的经历写「我在 X 里做了…」；教学示例写「这个演示实现里用 code/… 做了…」；尚未落地的方案写「如果由我实现，我会…」。Agent 岗几乎每道概念题后面都会跟「你们项目里具体怎么做的」，只背定义会在追问里露馅；但**没有真实经历时，宁可写「我没有对应经历，以下是可迁移的做法」也不要把教学代码改写成第一人称履历**。章 4 的「可能被继续深挖的点」优先预埋四类追问：换成 Workflow 行不行、怎么评估有效、出过什么故障、成本多少怎么降。

## 7. 教学示例 ≠ 候选人真实经历

| 来源类别 | 能写什么 | 禁止写什么 |
|---|---|---|
| **候选人已确认经历**（简历 / 作品集里本人明确提供） | 「我在 X 项目里负责…」，带可核对结果 | 把别人的项目、教学仓库、示范答案算进本人业绩 |
| **教学示例**（`code/*.py`、知识库 README、本题库） | 「这个演示实现里…」「教材里的机制是…」 | 「我做过 / 我实现过 / 我们项目里 / 我过往项目」 |
| **假设方案**（尚未落地的设计） | 「如果由我实现，我会…」「可行的方案是…」 | 「已完成的补足动作」「上线后提升了 N%」 |

- 文件存在只证明教学实现存在，**不证明候选人参与过**。
- 个人经历不足时给「可替换口径 + 待确认字段」，不要为满足「完整可朗读」「必须有项目证据」而补写经历。
- 章 6 的补足动作：**有证据才写已完成**，否则写「拟补足计划」并列出待确认前提。
- 脚本只做形式护栏（S34：`code/` 与第一人称完成式同句时给 warn）；**经历真实性由 `07` 的模型勾选项与用户本人确认**，校验通过不等于内容可信。
- 「满分、没有问题的真实回答」改称「**在已知材料与假设下可用的示范作答**」：字数、关键词、引用关系只能证明形式，不能证明答案相关、准确或来自本人。
