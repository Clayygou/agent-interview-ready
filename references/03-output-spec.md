# 03 · 输出文档规格

> 加载时机：步骤 6~7。校验阶段只读 `07` 与脚本报告。
> 目标：把「质量」翻译成脚本能验的数字规格，规则之间不打架。

## 1. 文档骨架（顺序固定）

| # | 章节 | 核心产出 |
|---|---|---|
| 0 | 使用说明与目录 | 元信息、面经检索状态、简历状态、推荐阅读顺序、图例 |
| 1 | 公司与岗位调研 | 7 项事实 + 3~5 条可直接说出口的公司理解 |
| 2 | 自我介绍 | 1 分钟版 + 3~5 分钟版，均可朗读 |
| 3 | 业务能力考察 | **章首 `### JD 题型映射`** + 按矩阵定量的专业题与**完整参考答案** |
| 4 | 简历深挖 | **章首 `### 简历针对性修改清单`** + 按矩阵定量的追问与应对 |
| 5 | 行为面试与个人特质 | 按矩阵定量的软素质题与 STAR 答案 |
| 6 | Gap 质疑题 | 1~3 道针对真实差距的说服性回答 |
| 7 | 反问问题 | 4~6 个低风险加分的反问 |
| 8 | 模拟面试记录与评判 | **仅交互版**：难度轨迹表 + 逐轮回答、难度、评分、失分点、改进口径、**示范作答**、总评表 |
| 附录 | 参考来源 | 分「公司资料」「面经」两组，编号可回溯 |

标题格式固定为 `## 0｜使用说明与目录` … `## 7｜反问问题`，交互版再加 `## 8｜模拟面试记录与评判`，最后 `## 附录｜参考来源`；脚本按模式校验顺序。紧凑版**不得**出现章 8。

章 3 / 章 4 的两个 `###` 小节是**章级内容**，写在第一个 Q 行之前，不计入单题字数；两种模式都必须有。

## 2. 文档头部（必须）

```markdown
# {公司} · {岗位} 面试准备
> 面试类型：业务面（一面）｜生成日期：YYYY-MM-DD｜信息来源：公开资料 + 用户简历 + 面经（如有）
> 面经检索：未检索到有效面经
> 简历状态：已解析（真实简历）
> 模式：紧凑版
```

- `模式：交互版`（默认）= 步骤 8 逐题模拟面试并含章 8；`模式：紧凑版` = 跳过交互、不含章 8，须在章 0 标注「未进行模拟面试」。脚本按此行决定是否检查章 8。
- `简历状态` 三态（脚本 S24 归一化）：`已解析（真实简历）` / `占位 / 演练代填` / `未提供`。三态决定章 4 的修改清单是**逐条硬要求**还是**边界说明**；此行缺失直接判不合格。
- 「更详细」= 在矩阵上限内加题、把章节写到预算上限，**不新增第三种模式、不突破硬上限**。

## 3. 篇幅与信息密度（硬约束）

- 全文有效字数 **8,000~13,000 字**（含表格文字，不含目录与附录来源），硬上限 13,000。
- 材料确实不足时可降至 7,000~8,000，须在章 0 标注信息边界；脚本给 `warn` 不阻断。
- 章节预算（单位：字）：

| 章节 | 业务面 | HR 面 |
|---|---|---|
| 0 使用说明 | 250~350 | 250~350 |
| 1 调研 | 1,200~1,800 | 1,200~1,800 |
| 2 自我介绍 | 800~1,100 | 800~1,100 |
| 3 业务题（含映射表 + ≥3 道八股） | 2,800~3,800 | 1,100~1,800 |
| 4 简历深挖（含修改清单） | 1,600~2,400 | 1,200~1,900 |
| 5 行为题 | 700~1,200 | 1,600~2,400 |
| 6 Gap | 400~900 | 400~700 |
| 7 反问 | 300~450 | 300~450 |
| 8 模拟面试记录与评判（仅交互版，5~7 轮） | 1,100~2,200 | 1,100~2,200 |

- 单题有效字数上限（脚本按题块统计）：章 3 常规 ≤300、方案 / 系统设计 ≤450 且最多 2 道；章 4 150~250；章 5 180~300；章 6 300~450；章 7 60~120。
- 上限不足时按「业务题 → 简历深挖 → 行为题 → 调研」补到预算上限，只能加事实、数据、案例与追问预埋，**不得重复或注水**；超限时**压缩单题表述与调研背景，不减题**——题量矩阵固定，脚本不识别「获准减题」例外。
- 同一事实只出现一次；不写章首摘要、章末速记、记忆锚点、客套铺垫、阅读时长。

## 4. 题目标记（脚本解析依据）

题目**不用四级标题**（手机端标题最多三级），统一用加粗行，行首格式固定：

```markdown
**Q3-1｜【基础八股】LLM 的自回归生成与训练推理差异**
**Q3-4｜业务面：怎么判断该用 Agent 还是 Workflow**
**Q4-2｜你在某项目里的职责边界到底到哪**
**Q7-1｜这个岗位入职前三个月最希望解决什么**
```

- 正则：`^\*\*Q(\d)-(\d+)｜(.+)\*\*$`，章节号与所在章必须一致，序号在章内连续。
- 归入 `basics` 题域的题目，标题必须以 `【基础八股】` 开头（见 `10` §3）。
- 脚本据此统计题量、切分题块、校验单题字数与跨章重复标题。

## 5. 每题固定输出

章 3 / 4 / 5 / 6 每题包含五项，用小标题或加粗短语，**不新增标题层级**：

| 项 | 说明 |
|---|---|
| 问题 | 即 Q 行 |
| 考察意图 | 一句话 |
| 答题框架 | 2~4 个编号分点 |
| **参考答案** | **「没有问题的真实回答」**：结论句 → ≥2 个编号分点 → 可核对证据 → 代价 / 边界 / 替代方案；≥100 有效字，可直接朗读 |
| 优先级 | `🔴 必背` 或 `🔵 加分`（必须带文字标签） |

**参考答案不是答题提纲，是这道题的满分作答本身**。判定标准：合上文档能把这段讲给别人听。脚本 S22 会拦：

- 缺 `**参考答案**` 行、有效字数 <100、没有编号分点、出现 `略 / 同上 / 见上文 / 见参考答案 / 待补 / TBD` 等占位词 → `error`；
- 缺证据锚（证据 / 项目 / `code/` / 题号 / 日志 / 评测集）或缺代价锚（代价 / 边界 / 替代 / 风险 / 失败 / 退化） → `warn`，须在语义自检里补上。

- **五项必须写成正文行**（Q 行 + 加粗短语行），不得放进 `>` 引用块；章级补充说明（章首提示、章末备用口径）写在题目之外，校验器统计单题字数时会排除它们。把答案正文塞进引用块以规避字数上限，视为不合格（脚本不验此项，属 `07` 模型勾选项）。
- 参考答案写成**一整行**（结论、分点、证据、代价在同一行），便于脚本按行解析；不要拆成多行后只写一句提纲。
- 章 4 每条额外预埋 1~2 个「可能被继续深挖的点」及应对方向。
- 章 5 统一 STAR（情境-任务-行动-结果），末尾补一句「本题想传递的个人特质」。
- 章 6 固定四步：承认差距 → 可迁移能力 + 证据 → 已完成的补足动作 → 动机与岗位价值；给完整参考答案 + 可替换措辞。
- 章 7 每个反问附一句「为什么问 / 想传递什么信号」，不需要参考答案。
- `【面经高频】` 标签最多 5 道，且必须与 evidence 的 `high_frequency_points` 对应。

## 6. 章 0 细则（250~350 字）

- 元信息：公司、岗位、面试类型（含原始表述）、生成日期、面经检索状态、简历状态、作品集使用状态。
- 推荐阅读顺序：业务面 `1 → 2 → 3 → 4 → 6`；HR 面 `1 → 2 → 5 → 6 → 7`。
- 考前速览路径：只看 `🔴 必背`、加粗句，以及章 8 的 `**示范作答**`。
- 样式图例（见 `06`）；多轮组合时末尾补 2~3 条「下一轮差异提示」。
- 降级留痕：JD 信息不足 / 简历占位 / 领域题库未接入 / 基础题库不足，都在这里写清。

## 7. 章 1 / 章 2 细则

**章 1 必须覆盖 7 项**：公司简介与主营业务、商业模式与收入来源、核心产品线及定位、文化与价值观、近 12 个月动态、行业位置与竞争格局、该岗位在组织中的角色。每项都要回答「与目标岗位有什么关系」；必须出现具体产品名 / 业务线 / 指标 / 战略动作，禁止百科式泛泛介绍。

**章 2 两版**：A ≤1 分钟（200~260 字）、B 3~5 分钟（600~900 字）。统一骨架 = 一句话定位 → 2~3 个支撑点（能力主张 + 成果 / 案例 + 数据）→ 与该公司该岗位的匹配（自然嵌入 JD 关键词）→ 一句话动机。第一人称口语化、可直接朗读；标停顿点 `/` 与可替换模块；两版事实必须一致。业务面重成果与专业深度，HR 面重稳定性、动机与文化匹配。

## 8. 附录格式

```markdown
## 附录｜参考来源

### 公司资料
1. [公司 2026 Q2 财报](https://…) — 官网，2026-08-15
2. [某产品线发布公告](https://…) — 官方公众号，2026-05-20

### 面经
3. [某岗位面经](https://…) — 牛客，2026-09-12
```

- 正文关键数据用 `[1]` `[2]` 标注；编号连续、合计 ≤20 条、两组分开。
- 无法给出链接时写「公开报道 / 官网，未附链接」，**不得编造出处**。
- 附录文字不计入 8,000~13,000 字有效字数。

## 9. 章 8 格式（交互版，脚本解析依据）

```markdown
## 8｜模拟面试记录与评判

> 模式：交互版｜共 6 轮（含 2 次追问）｜最高难度 L3｜评分 0~4｜首题种子 demo-seed-001

### 难度轨迹

| 轮次 | 难度 | 触发动作 | 得分 |
|---|---|---|---|
| 1 | L1 | 题库随机首题 | 3 |
| 2 | L1 | 追问：补代价 | 4 |
| 3 | L2 | 升档：换考点 | 3 |

**M1｜对应 Q3-1｜第 1 轮｜L1**
**回答**：（用户原文，或「未作答」）
**评分**：3 / 4｜有依据缺代价
**失分点**：回答里只讲了怎么实现，没说失败代价与替代方案。
**改进口径**：结论先行 → 依据 → 项目证据 → 代价与边界，四步补齐。
**考点索引**：INTERVIEW.md 第 37 题 / code/01_minimal_react_agent.py
**示范作答**：**结论先行**：…… 1. 依据…… 2. 证据…… 3. 代价与边界……（≥100 字，可直接朗读）

### 总评表

| 轮次 | 对应题 | 得分 | 最该补的一件事 |
|---|---|---|---|
| M1 | Q3-1 | 3 | 补代价与替代方案 |

本场最高难度 L3，下一场建议从 L2 起手。
**下轮优先复习**：1. 第 37 题 … 2. 第 26 题 … 3. 第 92 题 …
```

- M 行正则 `^\*\*M(\d+)｜对应 (Q\d-\d+)｜第 (\d+) 轮｜(L[1-4])\*\*$`；编号连续，`q_ref` 指向正文真实 Q 行，**难度标签必须与台账 `level` 一致**。
- 每组**六项固定顺序**：回答 / 评分 / 失分点 / 改进口径 / 考点索引 / **示范作答**，缺一即不合格。
- `**示范作答**` 是**这题没有问题的真实回答**：不评价用户、不复述用户原话、不写「略 / 见参考答案」，≥100 有效字，含结论 + 依据 + 可核对证据 + 代价与边界。用户答 0 分或选「这题我不会」时尤其要给全。脚本 S23 会拦缺失、过短、占位、与回答雷同。
- 评分只能是 `0 / 4` ~ `4 / 4` 加档位词；回答写「未作答」时必须 `0 / 4｜未作答`。
- **难度轨迹表必须有**，首列只写纯轮次数字（避免与总评表的 `M1` 行混淆），列数 ≤4、行数 = M 轮数；「触发动作」写 `题库随机首题 / 追问：<依据> / 升档：换考点 / 降档：<原因> / 保持：换考点 / 试探升档：换考点`（对应 `probe`，见 `09` §3.1），与台账 `decision.action` 一致。
- 总评表列数 ≤4、行数 = M 轮数；`下轮优先复习` 必须 3 条并引用真实题号；总评表后补一句最高难度与下一场起手档。
- 章 8 计入 8,000~13,000 字总有效字数，预算见 §3；轮数、追问上限见 `rules.json`；附录仍不计入。**提前结束（`ended_reason` ≠ `completed`）只保留已发生轮次，豁免目标轮数与最高难度目标**；最后一轮才得 4 分、0 轮取消都合法。
- 回答原文照抄，超过 200 字可标「节选」但须保留关键句；不得润色或替面试者补写。

## 10. 章 3 章首：JD 题型映射（两种模式都必须有）

格式与规则见 `10-jd-profile.md` §5。要点：

```markdown
### JD 题型映射

> JD 指纹：{公司}｜{岗位}｜{≥3 个 JD 关键词，/ 分隔}｜{面试类型}

| 题域 | JD 关键词 | 题量 | 对应 Q 编号 |
|---|---|---|---|
| basics | LLM / Transformer / PPO | 3 | Q3-1, Q3-2, Q3-3 |
| multimodal | 全模态 / VLM | 3 | Q3-4, Q3-5, Q3-6 |
```

- 4 列固定；题域名取 `10` §2 枚举；`对应 Q 编号` 的并集 = 章 3 全部 Q 编号（脚本 S25）。
- `basics` 题量：业务面 ≥3、**HR 面 0 下限**（HR 面由 `behavior` 题域 ≥2 题约束）；归入 `basics` 的题目标题必须带 `【基础八股】`（脚本 S26）。
- **不同 JD 不得复用同一张表**；题目内容要与题域相符（`07` 模型勾选项）。

## 11. 章 4 章首：简历针对性修改清单（两种模式都必须有）

```markdown
### 简历针对性修改清单

1. **位置**：项目经历第 2 条 → **问题**：只写「负责 Agent 开发」，没有结果与边界 → **改法**：改成「实现工具 Schema 校验与有限重试，把参数错误导致的重复调用从 X 次降到 Y 次」，并注明自己负责的模块 → **对应 JD**：工具调用 / 运行时可靠性
2. **位置**：技能清单 → **问题**：列了十个框架名，与 JD 关键词不重合 → **改法**：换成 JD 原词并各附一个项目文件 → **对应 JD**：Agent 工程
3. **位置**：自我评价 → **问题**：写「学习能力强」无证据 → **改法**：换成一次故障复盘的可核对结果 → **对应 JD**：故障定位
```

- **已解析（真实简历）**：≥3 条，每条必须含 `**改法**` 与 `**对应 JD**` 两个字段；`**对应 JD**` 要能与章 3 的 JD 指纹关键词对上（脚本 S24 验字段，语义对应由 `07` 勾）。
- **占位 / 演练代填**：清单里写明「需替换为真实简历」，可给 3 条通用改写方向但须标注「按该 JD 的通用建议，非针对本人经历」；不得把占位文本当真实经历改。
- **未提供**：写明「未提供简历，无法给出针对性修改」，并列出「拿到简历后优先核对的三处」；不编造经历。
- 改法只做**表达与证据口径**的调整，不虚构项目、数据、任职单位与任职年限（事实边界见 `06`）。
- 清单与章 4 题目不得重复：清单说「简历怎么改」，题目说「改完之后怎么被追问」。
